The fundamental difference

n8n

Editor graph serialization

An n8n export stores nodes as an array plus a separate edge map. It includes canvas coordinates, editor notes, credential references, workflow settings, test pinning, and sometimes instance-managed lifecycle metadata.

LAA workflow

Declarative executable definition

LAA stores named triggers and actions as objects. Dependencies live on each action through runAfter; nesting represents conditions, loops, scopes, and agent tools. Canvas coordinates are not part of the executable definition.

LAA template

Portable testable bundle

AutoTemplate v1 wraps the workflow with gallery metadata, sample trigger output, per-action mocks, and connector requirements. This is broader than an n8n workflow export because it packages a guided test experience.

Scope note: “Every n8n parameter” here means every documented/current field in the workflow envelope, INode, IConnections, IWorkflowSettings, and workflow groups. Both platforms also have polymorphic operation inputs: nodes[].parameters in n8n and triggers/actions.*.inputs in LAA. Those connector-specific properties are effectively unbounded catalogs and are compared structurally rather than pretending one static table can enumerate every Slack, SQL, SAP, HTTP, or AI-model field.

Identity

n8n puts workflow and node IDs in the payload. LAA template identity is gallery metadata; executable action identity is the property key.

Graph

n8n: centralized connections. LAA: decentralized runAfter plus structural nesting.

Testing

n8n: pinData. LAA: sample trigger plus per-action mocks or runForReal.

Runtime policy

n8n emphasizes workflow save/timeout/error defaults. LAA exposes per-trigger/action concurrency, retry, secure data, pagination, limits, and typed outputs.

Polymorphic node/action configuration

n8n nodes[].parameters

Node package owns the schema

The type and typeVersion select a node implementation. That node declares its own resource, operation, authentication, fields, collections, display conditions, defaults, and expression support. The exported JSON stores only chosen values—not the field schema itself.

Practical result: custom/community nodes can introduce arbitrary configuration shapes. n8n is more open-ended, but portability depends on the destination instance having the same node package and version.

LAA triggers/actions inputs

Operation type and connector contract own the schema

type, connector apiId/operationId, or service-provider identifiers determine the expected inputs. WDL also gives common structural fields such as runAfter, runtimeConfiguration, retryPolicy, splitOn, and nested actions.

Practical result: LAA is more explicit about orchestration and runtime policy in JSON; connector portability depends on declared app-scoped connection references being satisfied at import.

What this means in practice

n8n JSON is more editor-portable

It preserves visual layout, notes, grouping, node packages, selected parameter values, and test pinning. A workflow can look substantially the same after import—assuming node types and credentials exist.

LAA JSON is more deployment/runtime explicit

It has first-class workflow parameters and outputs, status-aware dependencies, nested orchestration, secure-data settings, local concurrency, rich retry policies, mock outcomes, trigger fixtures, and declared connection requirements.

Neither is a complete application backup

n8n exports reference credentials rather than embedding secrets. LAA templates declare connector types but require users to create/authenticate app-scoped connections; project/app RBAC, sandboxes, environment variables, and ownership are outside the template envelope.

Bottom line: n8n optimizes the JSON for a visual automation editor and an extensible node ecosystem. LAA optimizes for a declarative, governable execution contract and a gallery template that can be safely demonstrated with fixtures. The largest LAA-only strengths are typed runtime/deployment configuration and test bundles; the largest n8n-only strengths are canvas fidelity, node-level UX metadata, open node extensibility, persistent workflow state, and editor-oriented execution controls.
